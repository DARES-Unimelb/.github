\begin{summarybox}
This revision keeps the electronics work centred on \textbf{two major engineering objectives}: the competition flight-control and electrical system, and the motor test bench. It records the current development state, separates aircraft-level flight control from motor-level ESC control, and keeps supporting and future research streams distinct from the current core projects. Team leaders retain responsibility for selecting initial learning resources and implementation approaches, subject to interfaces, safety requirements and validation evidence.
\end{summarybox}

\section{Beginner onboarding \& project entry}

\begin{callout}[purple]
\textbf{Purpose.} Give new members a common, safe baseline before they enter a technical project. No previous experience is assumed. Complete and review the four milestones below in order.
\end{callout}

\begin{multicols}{2}
\begin{project}{01 \; Download the Ground Station}{purple}{Milestone 1}
Download and install the team-selected ground station. Open it successfully and connect to the approved simulator or training flight controller.
\end{project}

\begin{project}{02 \; Complete Basic Wiring}{slate}{Milestone 2}
Complete the approved training wiring for power, flight controller, receiver, telemetry, servos, ESC and required sensors. Check polarity, pinout and signal ground before power-on.
\end{project}

\columnbreak

\begin{project}{03 \; Complete Component Selection}{teal}{  Milestone 3}
Complete a short selection sheet for an assigned subsystem. Check voltage, current, interface or protocol, connector and overall system compatibility.
\end{project}

\begin{project}{04 \; Complete System Setup}{amber}{Milestone 4}
Complete basic configuration and calibration. Verify RC mapping, actuator direction, failsafe, telemetry and data logging during a bench check.
\end{project}
\end{multicols}

\begin{callout}[teal]
\textbf{Project team entry.} After all four milestones have been completed and reviewed by a project lead or experienced member, the beginner may join a project team and take a clearly scoped task.
\end{callout}

\section{System overview}

\Needspace{9\baselineskip}\begin{project}{01 \; Competition Flight-Control \& Electrical System}{purple}{Integrated aircraft system}
\lbl{Purpose} \; Develop the complete electronics and control system required for the NFC fixed-wing aircraft.

\lbl{Current development} \; Flight control; motor control / ESC; and battery management / power. Sensors and integration support these three streams; vision recognition is a separate future-facing task.

\lbl{Principle} \; Hardware and software are developed together inside each subsystem. The subsystem boundaries are engineering interfaces, not automatically separate projects.

\begin{callout}[purple]
\textbf{Control separation.} Aircraft flight-control law $\rightarrow$ motor/actuator command $\rightarrow$ ESC. The ESC currently uses six-step commutation and will later develop FOC. The aircraft flight controller may use a different control method; its control law remains to be selected.
\end{callout}
\end{project}

\Needspace{9\baselineskip}\begin{project}{02 \; Motor Test Bench}{teal}{Independent engineering deliverable}
\lbl{Role in current plan} \; Use the existing test bench to validate the present six-step ESC, support the later FOC implementation, and measure propulsion-system behaviour for the competition aircraft.

\lbl{Measurements} \; Thrust; RPM; voltage; current; electrical power; motor/ESC temperature; efficiency; command input; propeller performance.

\lbl{Existing base} \; Preserve and extend the current \texttt{Motor\_testing\_bench} repository and its history.

\lbl{Ownership} \; Existing contributors and the next project owner must be confirmed.
\end{project}

\begin{callout}[slate]
\textbf{Structure rule.} A new project should require an independent deliverable, defined inputs and outputs, sufficient work and active members, and a clear reason it cannot be managed as a subsystem of an existing project.
\end{callout}

\section{The projects}

Each project uses the same structure: purpose, black-box interface, ordered milestones, a broad tool stack, next-week actions, and a self-directed research brief. This keeps the project descriptions comparable while leaving implementation choices to the project leads.

% ---------------------------------------------------------------------------
\Needspace{9\baselineskip}\begin{project}{1 \, Flight \& Attitude Control}{purple}{Proposed: Rohan Lynch \textbullet{} Ash Zhang}
\lbl{Purpose} \; Develop and validate the aircraft-level guidance and control system for the NFC fixed-wing aircraft, converting pilot or mission objectives into safe actuator and propulsion commands.

\lbl{Black box} \; \textit{In:} state estimate, pilot or mission setpoints, link status, system-health status. \; \textit{Out:} aileron, elevator, rudder and throttle commands, flight mode, failsafe actions, and logged controller states.

\lbl{Milestones} \;
\M{0} aircraft requirements, model and baseline platform defined \;$\rightarrow$\;
\M{1} fixed-wing SITL running end to end \;$\rightarrow$\;
\M{2} rate loop, attitude loop and mixer/control allocation validated in simulation or HIL \;$\rightarrow$\;
\M{3} first-flight baseline and failsafe behaviour validated \;$\rightarrow$\;
\M{4} mission modes and predicted-vs-measured flight behaviour characterised for the FDR.

\lbl{Stack} \; PX4 or ArduPilot as the reference baseline; C/C++ on an STM32-class autopilot where in-house functions are required; MATLAB/Simulink or Python for plant modelling and analysis; SITL/HIL before flight testing.

\lbl{Next week} \; Define controlled states, sensor inputs, actuator outputs, performance targets and safety requirements; select the initial baseline; bring up a fixed-wing SITL; list the competition rules that affect control, failsafe and emergency behaviour.

\Needspace{9\baselineskip}\begin{project}{2 \, Motor Control \& ESC}{coral}{Transition: Jinghan $\rightarrow$ Jayden + Shangrui}
\lbl{Purpose} \; Develop the BLDC motor-drive and ESC hardware and firmware that converts the aircraft DC bus into controlled three-phase motor power with measurable performance and protection.

\lbl{Black box} \; \textit{In:} bus voltage, propulsion/throttle command, current and rotor-speed/position information where available. \; \textit{Out:} three-phase motor drive, RPM/current/temperature telemetry, and fault states.

\lbl{Milestones} \;
\M{0} present six-step implementation documented and reproducible \;$\rightarrow$\;
\M{1} six-step commutation stable on the bench and characterised on the motor test bench \;$\rightarrow$\;
\M{2} protection, current sensing and telemetry validated \;$\rightarrow$\;
\M{3} FOC current-control architecture implemented on development hardware \;$\rightarrow$\;
\M{4} FOC and six-step performance compared under the same test procedure.

\lbl{Stack} \; STM32F1/F4-class development hardware and existing ESC assets; ODrive-related development hardware; C/C++; oscilloscope and current measurement; OrCAD or KiCad for hardware; LTspice/PLECS where power-stage simulation is useful; SimpleFOC, VESC and AM32 as reference implementations.

\lbl{Next week} \; Freeze a one-page requirements sheet for voltage, current, motor Kv range, interfaces and protection; reproduce the current six-step setup; define the current-sensing and rotor-angle strategy required for FOC; agree the motor-test-bench measurements used for comparison.

\lbl{Black box} \; \textit{In:} battery cells, charge/discharge current, temperature and aircraft load demand. \; \textit{Out:} protected propulsion and avionics power, cell/pack measurements, balancing behaviour, health information and protection trips.

\M{3} balancing and charge/discharge behaviour validated \;$\rightarrow$\;
\M{4} power-distribution and ESC/avionics interfaces integrated and documented.

\lbl{Stack} \; FRBP-ESM-111A-KY as the reference design; OrCAD or KiCad for schematic/PCB review; LTspice where useful; battery logging/charge equipment; Python for measured data and comparison tables.

\lbl{Next week} \; Freeze pack voltage, current, temperature and interface requirements; record every retained and modified element relative to FRBP-ESM-111A-KY; define the bench-test procedure and acceptance criteria before approving hardware changes.

\Needspace{9\baselineskip}\begin{project}{4 \, Sensors \& State Estimation}{purple}{Supporting function; owner TBD}
\lbl{Purpose} \; Turn noisy and biased sensor measurements into a state estimate that the flight controller can trust and that can be validated against logged aircraft behaviour.

\lbl{Black box} \; \textit{In:} IMU, GPS, barometer, magnetometer, pitot/airspeed and timing information. \; \textit{Out:} attitude, angular rates, position, velocity, airspeed and estimator-health information for control and logging.

\lbl{Milestones} \;
\M{0} required states, sensors and update rates defined \;$\rightarrow$\;
\M{1} raw sensor data logged and characterised \;$\rightarrow$\;
\M{2} basic attitude estimate validated on a bench test \;$\rightarrow$\;
\M{3} GPS/barometer/magnetometer/airspeed fusion integrated \;$\rightarrow$\;
\M{4} estimator output compared with ground truth or an accepted reference during flight tests.

\lbl{Stack} \; Existing COTS-autopilot sensors as the initial baseline; Python or MATLAB for data analysis; complementary/Mahony-style attitude filters before EKF complexity; PX4/ArduPilot estimator implementations as references; standard flight-data logging.

\lbl{Next week} \; Define the state vector and update-rate requirements; choose the initial sensor source; establish the logging and ground-truth strategy; implement and test a basic complementary filter before expanding complexity.

\Needspace{9\baselineskip}\begin{project}{5 \, Vision Recognition \& Higher-Level Autonomy}{blue}{Separate task; vision recognition: David}
\lbl{Purpose} \; Develop vision-based perception that can support target/object recognition and higher-level navigation or autonomous decision-making without becoming a dependency for the first validated flight-control baseline.

\lbl{Black box} \; \textit{In:} camera images or video, aircraft pose/state estimate and mission context. \; \textit{Out:} detections, classifications or target/location information, confidence/health information, and logged perception results for later evaluation.

\lbl{Milestones} \;
\M{0} concrete competition-relevant vision deliverable and dataset defined \;$\rightarrow$\;
\M{1} offline detection/recognition baseline running on recorded data \;$\rightarrow$\;
\M{2} evaluation metrics and failure cases documented \;$\rightarrow$\;
\M{3} real-time or near-real-time inference demonstrated on the intended compute platform \;$\rightarrow$\;
\M{4} interface to navigation/autonomy tested in simulation or replay before any flight-critical use.

\lbl{Stack} \; Python; OpenCV; PyTorch or another selected learning framework; recorded and simulated image datasets; standard plotting/evaluation tools; a clearly defined message/interface to the navigation or autonomy layer.

\lbl{Next week} \; Define the exact vision deliverable, input source, output message and success metric; collect or identify a small representative dataset; build one reproducible baseline; document how the vision result would be consumed without directly taking over low-level flight control.

\Needspace{9\baselineskip}\begin{project}{6 \, Motor Test Bench}{teal}{Independent engineering deliverable; owner TBD}

\lbl{Black box} \; \textit{In:} motor, propeller, ESC, supply and throttle profile. \; \textit{Out:} thrust, RPM, voltage, current, electrical power, temperature, efficiency and a logged dataset tied to the test configuration.

\lbl{Milestones} \;
\M{0} existing bench inventoried and measurands/accuracy targets defined \;$\rightarrow$\;
\M{1} thrust, RPM, voltage and current acquisition calibrated \;$\rightarrow$\;
\M{2} first repeatable motor/prop/ESC map completed \;$\rightarrow$\;
\M{3} automated throttle sweeps and temperature/efficiency logging implemented \;$\rightarrow$\;
\M{4} test datasets used to compare six-step and FOC ESC performance and support the aircraft propulsion model.

\lbl{Stack} \; Existing \texttt{Motor\_testing\_bench} repository and hardware; load-cell measurement; RPM sensing; voltage/current sensing; STM32 or Arduino-class DAQ where appropriate; Python for acquisition, plotting and result comparison.

\lbl{Next week} \; Photograph and inventory the existing bench; define the measurement list and target accuracy; verify calibration for thrust, voltage, current and RPM; run one controlled baseline test and record every test condition needed to reproduce it.
